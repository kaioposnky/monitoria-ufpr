# ADR-007: Comunicação por API REST (HTTP/JSON) com contrato documentado

Status: aceita.

## Contexto

Com frontend e backend separados ([ADR-006](ADR-006.md)), foi preciso definir como a SPA conversa com o backend ([ADR-001](ADR-001.md)). A mesma forma de comunicação precisa servir também a clientes futuros, como um aplicativo mobile, sem depender de sessão ou de páginas montadas pelo servidor.

## Problema e forças envolvidas

Ter um contrato claro, sem estado de sessão (ASR-02), simples de usar no navegador e fácil de testar e documentar para uma equipe pequena (ASR-03), sem acrescentar ferramentas ou infraestrutura desnecessárias para o tamanho do sistema.

## Alternativas consideradas

1. **GraphQL:** permite consultas flexíveis por um único endereço, mas acrescenta esquemas e configuração extra no cliente e no servidor e combina menos com o cache por consulta.
2. **gRPC:** usa contratos binários eficientes, mas não funciona direto no navegador sem um intermediário, o que dificulta usá-lo na SPA e depurar as chamadas.
3. **Endpoints por ação, sem padrão de recursos:** deixa as rotas menos uniformes e dificulta padronizar métodos, códigos de resposta e documentação.
4. **API REST sobre HTTP/JSON, versionada e documentada:** combina com o modelo de recursos do sistema e com os métodos HTTP.

## Decisão

Usar REST sobre HTTP/JSON. Todos os recursos ficam sob um prefixo com versão (/api/v1) e usam os métodos HTTP de forma padronizada (GET para consultar, POST para criar, PUT e PATCH para alterar, DELETE para remover). A única exceção é a exportação da agenda, que devolve um arquivo de calendário (.ics) em vez de JSON.

Os dados recebidos são validados no backend. Os erros seguem um formato JSON único com o código HTTP correspondente (400, 401, 403, 404 ou 409). O usuário se identifica enviando o token em cada requisição ([ADR-003](ADR-003.md)). No frontend, todas as chamadas passam por um único módulo, e a documentação do contrato (OpenAPI/Swagger) é gerada automaticamente a partir do código.

## Consequências positivas

HTTP/JSON funciona direto no navegador e em qualquer aplicativo ou script, sem bibliotecas proprietárias. O uso padronizado de métodos e códigos HTTP simplifica o tratamento de erros no frontend e os testes da API. A documentação gerada a partir do código acompanha o que a API realmente aceita e devolve.

## Consequências negativas, custos e riscos

Algumas telas precisam de várias requisições ou de respostas específicas para não trazer dados demais ou de menos. A comunicação é síncrona, ou seja, o cliente espera a resposta (para integrações externas, a falha é tratada como descrito na [ADR-004](ADR-004.md)). Mudanças incompatíveis na API vão exigir uma nova versão (/api/v2) ou um período em que as duas versões convivam.
