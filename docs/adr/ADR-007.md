# ADR-007: Comunicação via API REST (HTTP/JSON) com contrato OpenAPI

Status: aceita.

## Contexto

Com a decisão de separar frontend e backend ([ADR-006](ADR-006.md)), tornou-se necessário definir o estilo e o protocolo de comunicação entre a SPA React e o monólito Spring Boot ([ADR-001](ADR-001.md)), garantindo também que futuros clientes (como um aplicativo mobile) consigam consumir os mesmos serviços sem acoplamento a sessão HTML ou cookies de formulário.

## Problema e forças envolvidas

Estabelecer um contrato explícito, stateless (ASR-02), simples de consumir via fetch no navegador e fácil de testar e documentar para uma equipe pequena (ASR-03), sem introduzir ferramentas de serialização ou infraestrutura desnecessárias para o porte do domínio.

## Alternativas consideradas

1. **GraphQL:** permite consultas flexíveis em um único endpoint, mas adiciona complexidade de schemas/resolvers, tratamento extra contra consultas N+1, menor alinhamento direto com o cache por método/endpoint e curva adicional de configuração no cliente e servidor.
2. **gRPC:** oferece contratos binários performáticos via Protobuf, porém não roda nativamente no navegador sem proxy intermediário (gRPC-Web), dificultando depuração direta e consumo simples na SPA.
3. **Endpoints RPC ad-hoc baseados em ações:** reduz a uniformidade das rotas e dificulta padronizar métodos HTTP, códigos de status e documentação.
4. **API REST sobre HTTP/JSON (/api/v1/...) documentada com OpenAPI/Swagger:** alinha-se nativamente ao modelo de recursos do sistema, aos verbos HTTP e ao ecossistema Spring WebMVC.

## Decisão

Adotar **REST sobre HTTP/JSON** com versionamento de URI sob o prefixo /api/v1/** para todos os recursos do domínio (auth, cursos, disciplinas, materias, cursos-disciplinas, vagas-monitoria, candidaturas, monitores, horarios-atendimento, registros-atividades, usuarios e agenda), utilizando os verbos semânticos GET, POST, PUT, PATCH e DELETE e DTOs imutáveis (record). Exceção controlada ocorre em GET /api/v1/agenda/calendario.ics, que retorna text/calendar conforme RFC-5545.

As entradas são validadas com Bean Validation (@Valid), as respostas de erro seguem formato JSON padronizado pelo GlobalExceptionHandler (400, 401, 403, 404, 409), a autenticação trafega no cabeçalho Authorization: Bearer {token} ([ADR-003](ADR-003.md)), o consumo no frontend fica centralizado em frontend/src/shared/api/http.ts e a especificação do contrato é gerada automaticamente via OpenApiConfig (springdoc-openapi) em /v3/api-docs e /swagger-ui.html.

## Consequências positivas

O protocolo HTTP/JSON funciona nativamente em navegadores (fetch) e em qualquer cliente mobile ou script externo sem SDKs proprietários. A semântica padrão de verbos e status HTTP simplifica o tratamento de erros em http.ts e os testes de integração com MockMvc. Além disso, a documentação interativa no Swagger UI mantém o contrato de entrada, saída e segurança Bearer sempre atualizado a partir do código Java.

## Consequências negativas, custos e riscos

Telas compostas podem exigir múltiplas requisições ou DTOs específicos para evitar *over-fetching* e *under-fetching*. A comunicação é síncrona no ciclo requisição/resposta (mitigada para integrações externas via IntegracaoExecutor, conforme [ADR-004](ADR-004.md)). Por fim, alterações incompatíveis de payload exigirão controle de versão na URI (/api/v2/...) ou período de convivência para não quebrar clientes existentes.
