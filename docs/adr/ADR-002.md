# ADR-002: Banco relacional PostgreSQL com migrações versionadas

Status: aceita.

## Contexto

Os dados do sistema (cursos, disciplinas, matérias, usuários, vagas, candidaturas, monitores, horários e registros de atividade) são fortemente ligados entre si. Uma candidatura pertence a um aluno e a uma vaga, um monitor vem de uma candidatura, e assim por diante. Também há regras de unicidade, como um aluno não poder se candidatar duas vezes à mesma vaga. Durante o projeto, a estrutura do banco mudou algumas vezes, por exemplo ao separar disciplinas de matérias.

## Problema e forças envolvidas

Garantir transações confiáveis, integridade entre os dados e um histórico reproduzível das mudanças na estrutura do banco. Ao mesmo tempo, o protótipo e os testes precisam rodar em qualquer máquina sem instalar um servidor de banco (ASR-03).

## Alternativas consideradas

1. PostgreSQL com a estrutura gerada automaticamente pelo framework a partir do código: é rápido no começo, mas não guarda histórico das mudanças e pode alterar o banco de forma imprevisível.
2. Banco de documentos (MongoDB): não exige estrutura fixa, mas passaria para o código a responsabilidade de garantir as ligações entre os dados, que aqui são estáveis e bem definidas.
3. PostgreSQL com migrações versionadas (scripts numerados que registram cada mudança) e um banco em memória compatível para desenvolvimento e testes.

## Decisão

Usar PostgreSQL como banco principal, com a estrutura controlada por migrações versionadas. A aplicação confere, ao iniciar, se o código e o banco estão de acordo. Para desenvolvimento local e testes, usar um banco em memória (H2) em modo compatível com PostgreSQL, sem precisar instalar nada.

## Consequências positivas

O próprio banco garante as ligações e as regras de unicidade. As migrações deixam registrado como o modelo evoluiu (ver [MODELAGEM_BANCO.md](../../MODELAGEM_BANCO.md)), e uma divergência entre código e banco aparece logo ao iniciar a aplicação. Qualquer pessoa da equipe roda a API e os testes sem instalar PostgreSQL.

## Consequências negativas, custos e riscos

As migrações precisam funcionar tanto no PostgreSQL quanto no banco em memória, o que impede usar recursos exclusivos do PostgreSQL. Nos testes automatizados, a estrutura é criada direto a partir do código, então eles não comprovam que as migrações rodam no PostgreSQL real. Além disso, as entidades se referenciam por identificador, e não por objetos ligados, por isso a camada de serviços precisa conferir se os registros relacionados existem antes de salvar.
