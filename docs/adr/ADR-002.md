# ADR-002: Persistência relacional com PostgreSQL e migrações Flyway

Status: aceita.

## Contexto

Cursos, disciplinas, matérias, usuários, vagas, candidaturas, monitores, horários de atendimento e registros de atividades possuem diversas chaves estrangeiras (curso_id, disciplina_id, professor_id, vaga_id, aluno_id, candidatura_id, monitor_id), restrições CHECK e regras de unicidade (email, matricula, codigo, (vaga_id, aluno_id)). Além disso, o schema evoluiu incrementalmente com a inclusão de hash de senha (V3), janela de inscrição (V4) e separação entre disciplinas e matérias (V5).

## Problema e forças envolvidas

Garantir transações ACID, integridade referencial e versionamento reproduzível de schema em produção sem permitir alterações implícitas do ORM, e ao mesmo tempo permitir que o protótipo e a suíte de testes rodem localmente sem exigir instalação prévia de um servidor PostgreSQL (ASR-03).

## Alternativas consideradas

1. PostgreSQL com schema gerenciado pelo Hibernate (spring.jpa.hibernate.ddl-auto=update): rápido inicialmente, porém não versiona alterações históricas nem garante migrações seguras como a reestruturação de V5.
2. Banco de documentos (MongoDB): dispensa schema rígido no banco, porém transfere validação referencial e junções para o código Java sem que os dados tenham estrutura variável.
3. PostgreSQL com migrações versionadas via Flyway (V1 a V5) e ddl-auto=validate, usando H2 em memória (MODE=PostgreSQL) nos perfis dev e test.

## Decisão

Adotar PostgreSQL como banco relacional primário no perfil padrão (application.properties), com schema versionado pelo Flyway (classpath:db/migration, scripts V1 a V5) e spring.jpa.hibernate.ddl-auto=validate. Para desenvolvimento local e testes automatizados sem infraestrutura externa, manter H2 em memória com MODE=PostgreSQL no perfil dev (com Flyway ativo) e no perfil test (ddl-auto=create-drop e Flyway desabilitado). Os relacionamentos entre entidades JPA utilizam chaves Long explícitas com spring.jpa.open-in-view=false.

## Consequências positivas

O próprio banco assegura integridade referencial, unicidades e CHECKs desde o boot da aplicação, enquanto o Flyway mantém histórico auditável da evolução do modelo (MODELAGEM_BANCO.md). O ddl-auto=validate falha rapidamente caso entidades JPA e scripts SQL divirjam. Quem desenvolve ou testa o projeto consegue executar toda a API e os testes com ./mvnw sem instalar PostgreSQL localmente.

## Consequências negativas, custos e riscos

Os scripts de migração (V1–V5) precisam usar SQL compatível tanto com PostgreSQL quanto com o H2 em MODE=PostgreSQL (por exemplo, evitando recursos exclusivos do PostgreSQL sem alternativa no H2). No perfil test, como o Flyway fica desligado (ddl-auto=create-drop), os testes de integração não validam diretamente os scripts SQL de migração — essa validação depende do perfil dev ou da execução contra PostgreSQL. Adicionalmente, o uso de IDs Long em vez de @ManyToOne navegáveis exige que os services validem manualmente a existência das chaves estrangeiras antes de persistir.
