# ADR-002: Persistência relacional com PostgreSQL + Flyway e cache em memória

Status: aceita.

## Contexto

Cursos, matérias, usuários, vagas, candidaturas, monitores, horários e registros têm várias chaves estrangeiras, restrições de unicidade (`email`, `matricula`, `codigo`, `(vaga_id, aluno_id)`) e regras de estado. Em paralelo, consultas ao catálogo, vagas, monitores e horários se repetem bastante no início de cada semestre (ASR-01). Durante o desenvolvimento, o projeto chegou a ter configuração de Redis externo, depois substituída por cache em memória local.

## Problema e forças envolvidas

Preservar transações ACID e restrições relacionais no banco, responder leituras repetidas sem ir ao PostgreSQL toda vez (ASR-01) e não obrigar quem desenvolve ou testa o projeto a instalar e subir um servidor Redis separado (ASR-03).

## Alternativas consideradas

1. PostgreSQL puro sem cache: simples, mas envia cada consulta de vagas, matérias, monitores e horários direto ao banco.
2. PostgreSQL + Redis: resolve cache compartilhado entre réplicas, mas exige subir um serviço extra para um sistema pequeno de setor acadêmico.
3. Banco de documentos (MongoDB): dispensa schema rígido no banco, porém joga validação referencial e junções para o código Java sem que os dados tenham formato variável.

## Decisão

Usar PostgreSQL com migrações Flyway (`V1` a `V4`) e `spring.jpa.hibernate.ddl-auto=validate` no perfil padrão (H2 em memória nos perfis `dev` e `test`). Para cache-aside, habilitar Spring Cache (`ConcurrentMapCacheManager` via `spring.cache.type=simple`) nos services de catálogo, vagas, monitores e horários, invalidando as entradas com `@CacheEvict` e `@Caching` nas operações de escrita.

## Consequências positivas

Integridade referencial, unicidades e `CHECK`s ficam garantidos já no banco (`V1`–`V4`). Leituras repetidas de catálogo, vagas, monitores e horários saem da memória sem query SQL (verificado em `CacheAsideIntegrationTest`) e sem precisar instalar Redis localmente. Caso o sistema passe a rodar com várias instâncias no futuro, trocar para Redis altera configuração e `CacheConfig`, mantendo `@Cacheable` e `@CacheEvict` nos services.

## Consequências negativas, custos e riscos

O `ConcurrentMapCacheManager` vive só dentro da JVM daquela instância: se houver duas réplicas do backend atrás de um balanceador, os caches não sincronizam entre si. O provedor `simple` também não aplica TTL nem limite de entradas por padrão, então atualizações feitas manualmente direto no SQL do banco (fora da API) deixam dados antigos em memória até a próxima escrita ou reinício. Se o catálogo crescer muito, dá para trocar para Caffeine ou Redis sem mexer nas regras de negócio.
