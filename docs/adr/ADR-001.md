# ADR-001: Monólito em camadas no backend com SPA React separada

Status: aceita.

## Contexto

O sistema cobre cadastro de cursos e matérias, publicação de vagas, candidaturas, alocação de monitores, horários de atendimento e registro de atividades. No começo do projeto, o frontend chegou a usar NestJS com renderização no servidor (SSR), mantendo dois processos Node/Java para servir o mesmo conjunto de telas.

## Problema e forças envolvidas

Manter um único lugar para regras de negócio e controle de acesso (ASR-02), reduzir o trabalho de subir e implantar o sistema para uma equipe pequena (ASR-03) e não impedir que outros clientes (como um app mobile) consumam a API no futuro.

## Alternativas consideradas

- Manter SSR no servidor (NestJS SSR ou Thymeleaf), sustentando um runtime de apresentação acoplado ou separado sem demanda de SEO.
- Quebrar o backend em microsserviços (catálogo, seleção, atividades) com deploys e bancos independentes.
- Monólito em camadas no Spring Boot + SPA estática em React/Vite, deixando regras e segurança na API REST e entregando a UI como arquivos estáticos.

## Decisão

Adotar monólito em camadas no Spring Boot (`controller`, `security`, `service`, `repository`, `entity`, `dto`, `integration`, `exception`, `config` em `com.sistema`) combinado com SPA em React, TypeScript e Vite consumindo `/api/v1/**`.

## Consequências positivas

As regras de validação e permissão ficam só no backend, e a entrega em produção se resume a um JAR Spring Boot e à pasta `frontend/dist` atrás de um proxy `/api`. Como a API já sai documentada via OpenAPI (`/v3/api-docs`), novos clientes HTTP podem reutilizar os mesmos endpoints.

## Consequências negativas, custos e riscos

A SPA exige JavaScript habilitado no navegador e fallback de rotas para `index.html` no servidor HTTP, além de não entregar páginas pré-renderizadas para indexação por buscadores. Dentro do backend, os pacotes estão divididos por camada técnica e não por domínio, então qualquer service importa livremente repositórios de outras tabelas (como `HorarioAtendimentoService`, que importa 5 repositórios). Se o projeto crescer e precisar de fronteiras estritas entre subdomínios, será necessário reorganizar os pacotes por módulo de negócio.
