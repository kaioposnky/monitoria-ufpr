# ADR-005: Cache em memória para leituras repetidas

Status: aceita.

## Contexto

Consultas ao catálogo (cursos, disciplinas, matérias), às vagas, aos monitores e aos horários de atendimento se repetem muito, principalmente no início do semestre, enquanto esses dados mudam pouco (ASR-01). Durante o desenvolvimento, o projeto chegou a usar um Redis externo, removido depois por exigir infraestrutura a mais para um sistema de um setor acadêmico (ASR-03).

## Problema e forças envolvidas

Evitar consultas repetidas ao banco nessas leituras (ASR-01), não devolver dados desatualizados depois de uma alteração e não obrigar quem desenvolve, testa ou implanta o sistema a manter um servidor de cache separado (ASR-03).

## Alternativas consideradas

1. Sem cache: é mais simples, mas toda leitura repetida vai ao banco.
2. Cache distribuído com Redis: permite compartilhar o cache entre várias cópias do backend, mas exige mais um serviço para instalar e operar.
3. Cache em memória dentro da própria aplicação, usando o recurso de cache do Spring, com possibilidade de trocar de provedor depois só por configuração.

## Decisão

Usar cache em memória dentro da aplicação, na estratégia conhecida como cache-aside: na primeira leitura o dado vem do banco e fica guardado; nas leituras seguintes, sai direto da memória. Quando uma alteração é concluída com sucesso, os dados afetados saem do cache e são buscados de novo na próxima leitura. Só os dados de consulta frequente usam cache. Candidaturas, registros de atividade e usuários ficam de fora, porque mudam com mais frequência ou são dados pessoais.

## Consequências positivas

Depois da primeira consulta, as leituras repetidas não acessam o banco, o que é confirmado por teste automatizado. Nada precisa ser instalado além da própria aplicação. Uma alteração que falha não apaga o cache sem motivo. Se o sistema passar a rodar em várias cópias, é possível trocar para um cache distribuído com pouca mudança de código.

## Consequências negativas, custos e riscos

Cada cópia do backend tem seu próprio cache, e as cópias não se sincronizam. Por isso, rodar várias cópias exigiria um cache compartilhado. Os dados também não expiram sozinhos e não há limite de tamanho. Se alguém alterar o banco por fora da aplicação, o cache continua mostrando o dado antigo até a próxima alteração feita pela aplicação ou até ela reiniciar.
