# ADR-006: Frontend (SPA) separado do backend em vez de MVC tradicional

Status: aceita.

## Contexto

Em aplicações Spring Boot, é comum usar o MVC tradicional, em que o próprio servidor monta as páginas HTML a partir de templates. No início deste projeto também foi testada a renderização das páginas em um servidor Node separado. Ao consolidar a arquitetura, a equipe decidiu separar totalmente a interface (frontend) da aplicação servidora (backend).

## Problema e forças envolvidas

Organizar frontend e backend para facilitar a manutenção e a evolução de cada lado, usar em cada um ferramentas adequadas ao seu papel, aproveitar o que a equipe já conhece (ASR-03) e manter todas as regras de negócio e de acesso no servidor, sem prender o backend a um único tipo de cliente (ASR-02).

## Alternativas consideradas

1. **MVC tradicional no servidor:** tudo fica em um só projeto, mas telas, rotas e regras de negócio passam a ser construídas e publicadas juntas, e a interface fica menos interativa.
2. **Renderização das páginas em um servidor Node separado:** separa a interface do backend, mas mantém um segundo servidor rodando o tempo todo só para montar páginas, o que não traz ganho para um sistema interno que não depende de mecanismos de busca.
3. **Frontend como SPA separado e backend como API:** o navegador carrega a interface uma vez, e ela conversa com o servidor apenas pela API (ver [ADR-007](ADR-007.md)).

## Decisão

Separar frontend e backend. O backend cuida apenas de regras de negócio, dados, segurança e integrações externas. O frontend é uma SPA em React que roda no navegador e usa somente a API.

## Consequências positivas

- **Manutenção e evolução:** mudanças visuais ou de telas acontecem no frontend sem risco de quebrar regras de negócio ou segurança. O backend pode evoluir ou atender novos clientes, como um aplicativo mobile, sem duplicar regras.
- **Ferramenta certa para cada lado:** cada parte usa tecnologias próprias para sua função, em vez de limitar a interface a páginas montadas pelo servidor.
- **Conhecimento da equipe:** a equipe já tinha experiência com React no frontend e com Java e Spring no backend, o que reduziu o tempo de aprendizado.

## Consequências negativas, custos e riscos

São dois projetos, cada um com seu processo de build, testes e verificação. Também é preciso configurar a comunicação entre os dois (permitir as chamadas do navegador à API ou usar um redirecionamento) e fazer o servidor de arquivos entregar a SPA em qualquer rota. Como a interface roda no navegador, ela depende de JavaScript e não é bem indexada por buscadores, o que é aceitável para um sistema acadêmico interno.
