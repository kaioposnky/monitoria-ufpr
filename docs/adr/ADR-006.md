# ADR-006: Separação entre Frontend (SPA) e Backend em vez de MVC tradicional

Status: aceita.

## Contexto

Em sistemas web em Spring Boot, uma abordagem comum é o padrão MVC tradicional acoplado no servidor, no qual controllers retornam views renderizadas por templates HTML (como Thymeleaf ou JSP) dentro do mesmo projeto e processo do backend. No início deste projeto também houve experimentação com NestJS realizando renderização no servidor (SSR), mantendo um servidor Node separado para compor páginas. Ao consolidar a arquitetura do sistema de monitoria, optou-se por separar completamente a interface do usuário (frontend/) da aplicação servidora (backend/).

## Problema e forças envolvidas

Organizar frontend e backend de modo a facilitar a manutenção contínua e a evolução independente do sistema, permitir o uso de tecnologias mais modernas e especializadas em cada camada, aproveitar o conhecimento prévio da equipe para reduzir riscos e retrabalho (ASR-03) e manter todas as regras de negócio e autorização centralizadas no servidor sem amarrar o backend a um único tipo de cliente (ASR-02).

## Alternativas consideradas

1. **MVC tradicional server-side (Spring MVC + Thymeleaf/JSP):** mantém tudo em um único projeto Java, mas acopla ciclo de build, renderização de tela e rotas de navegação ao backend, além de oferecer menor ergonomia para fluxos interativos e componentes reutilizáveis na UI.
2. **SSR separado em Node (NestJS SSR):** separa a camada visual do Spring Boot, porém mantém dois servidores de aplicação rodando continuamente apenas para renderizar HTML em um sistema acadêmico sem demanda relevante de SEO.
3. **Frontend SPA separado + Backend API independente:** divide claramente apresentação (SPA estática servida ao navegador) e servidor de domínio/dados, comunicando-se exclusivamente por contrato de API (detalhado na [ADR-007](ADR-007.md)).

## Decisão

Adotar arquitetura com frontend e backend separados, abandonando o modelo MVC tradicional acoplado no servidor. O backend em **Java 21 + Spring Boot 4.1.2** concentra exclusivamente regras de negócio, persistência, segurança e integrações externas, enquanto o frontend em **React 19 + TypeScript + Vite 8 + React Router 7** (frontend/src) funciona como uma SPA independente estruturada por app/, pages/, components/, features/ e shared/.

## Consequências positivas

- **Melhor manutenção e evolução:** mudanças visuais, reorganização de telas, validações de formulário ou atualizações de dependências de interface acontecem no diretório frontend/ sem risco de quebrar regras de negócio, transações ou segurança no backend. Da mesma forma, o backend pode evoluir internamente ou atender novos clientes (como um aplicativo mobile institucional ou scripts de integração) sem duplicar regras.
- **Stacks mais adequadas por camada:** em vez de limitar a interface a templates HTML renderizados no servidor, cada lado utiliza ferramentas modernas e maduras para seu propósito (React/TypeScript/Vite/Vitest/Oxlint na UI e Spring Boot/Spring Security/JPA/Flyway no servidor).
- **Aderência à stack que o time já domina:** a equipe já possui experiência prática com React/TypeScript no frontend e Java/Spring Boot no backend, o que acelera o desenvolvimento, melhora a qualidade do código e reduz a curva de aprendizado durante o projeto.

## Consequências negativas, custos e riscos

A separação exige manter dois projetos com ciclos de build, testes e linters próprios (Maven no backend/ e npm/Vite no frontend/), configurar CORS (CorsConfig) ou proxy reverso /api (vite.config.ts em dev e proxy HTTP em produção), além de configurar fallback de rotas para index.html no servidor de estáticos. Por ser uma SPA executada no navegador, a interface depende de JavaScript habilitado e não entrega HTML pré-renderizado para indexação por buscadores — um custo aceitável para um sistema acadêmico interno.
