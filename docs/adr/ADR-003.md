# ADR-003: Autenticação com JWT e verificação de acesso a cada requisição

Status: aceita.

## Contexto

Nas primeiras versões das telas não havia login: o próprio usuário digitava seu identificador nos formulários. Assim, qualquer pessoa podia agir em nome de outra. O sistema precisa controlar quem cria vagas, quem se candidata, quem avalia candidaturas e quem lança horários e atividades (ASR-02).

Existe ainda um caso específico: ser monitor não é um tipo fixo de usuário. Um aluno se torna monitor quando é aprovado em uma vaga e pode deixar de ser no meio do semestre, sem que sua conta mude. A permissão de monitor depende, portanto, de um dado que muda com o tempo.

## Problema e forças envolvidas

Confirmar no backend quem é o usuário e se ele tem direito sobre o recurso pedido, sem guardar sessão no servidor. Além disso, quando um aluno vira monitor ou é desligado, a mudança precisa valer já na próxima requisição.

## Alternativas consideradas

- Sessão tradicional guardada no servidor: mantém estado em memória e dificulta escalar ou atender clientes diferentes.
- Guardar no token a informação de que o usuário é monitor: se ele for desligado ou recém-aprovado, o token continua com a informação antiga até expirar.
- Token JWT só com a identidade do usuário, mais uma verificação que consulta o banco a cada requisição para saber se ele é dono do recurso ou monitor ativo.

## Decisão

Usar autenticação com token JWT assinado, sem sessão no servidor, e senhas guardadas com hash. O token informa apenas quem é o usuário e seu tipo de conta (aluno, professor ou administrador). Em cada operação protegida, um componente de verificação de acesso (AccessGuard) consulta o banco para saber se o usuário é dono do recurso ou monitor ativo.

## Consequências positivas

O servidor não guarda sessão, e as regras de acesso ficam em um único componente, separadas das regras de negócio. Quando um professor efetiva um monitor, ele já pode cadastrar horários e atividades na requisição seguinte, sem fazer login de novo. Quando o recurso pedido não existe, o sistema responde "não encontrado" em vez de "acesso negado", o que facilita entender o erro.

## Consequências negativas, custos e riscos

Cada operação protegida faz consultas extras ao banco para conferir posse ou vínculo. Algumas listagens gerais ficam abertas a qualquer professor, e a interface filtra o que é exibido. Não há renovação nem revogação de token: um token emitido vale até expirar (8 horas) ou até a conta ser desativada. Os usuários de exemplo usam uma senha fixa, que precisa ser trocada antes de qualquer uso real.
